# 数据库选型与 118 MariaDB 评估

## 当前决定

认证系统当前使用独立 SQLite WAL 数据库，位于 118 的非 Web 目录。它不复用 118 原有 MariaDB 5.5，也不与旧系统共享账号、表或事务。

## 2026-08-30 只读检查结果

- 系统：CentOS 7.9、glibc 2.17。
- 现有数据库：MariaDB 5.5.68，监听 3306 全网卡。
- 数据目录约 240 MB，约 34 个业务/系统库、197 个表定义。
- 存在至少 62 组 MyISAM 数据和索引文件，没有独立 `.ibd` 文件。
- 检查时存在来自其他内网主机的持续连接。
- 多套本机 PHP 程序直接依赖该实例。
- 历史日志记录过 `mysql` 权限表及多个业务表的损坏检查。
- 只找到少量业务库的独立 SQL 备份，未发现覆盖全部实例的近期可验证备份。

因此不得为了认证系统原地升级、重启或复用该实例。MariaDB 5.5 已停止维护，后续应把旧业务迁移作为单独项目处理，而不是混入认证系统发布。

## 原地升级的影响

- 必须安排所有依赖系统停机；
- 必须先取得完整逻辑备份、物理备份和恢复演练结果；
- 需要先检查或修复已标记异常的 MyISAM 和系统表；
- 需要替换跨大版本 RPM、审查所有中间版本的不兼容项并运行 `mariadb-upgrade`；
- PHP 驱动、字符集、排序规则、SQL 模式、保留字和旧查询可能发生兼容问题；
- 大版本降级不受支持，失败时主要恢复方式是还原备份。

## 后续可选方案

1. 继续使用 SQLite：适合当前单实例、低并发企业内网认证，风险最低。
2. 新建完全独立数据库实例：单独端口、数据目录、服务账号和备份，不替换原 MariaDB；先在测试环境完成兼容验证。
3. 将旧 MariaDB 升级作为独立迁移项目：逐库盘点、建立全量备份和恢复演练、兼容性测试后再安排停机窗口。

在出现多认证节点、显著并发写入、跨节点高可用或专业数据库备份要求之前，不因“统一技术栈”而把认证系统接入高风险旧实例。
